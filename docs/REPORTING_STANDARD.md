# 报告编制规范

本规范适用于CES生成的仓库日报、周期总结、代码分析、项目测试审查及知识文档。
报告应使用准确、客观、可核验的工程表述，内容详略与变更复杂度及证据充分性相匹配。

## 报告名称与术语

| 用途 | 规范名称 |
| --- | --- |
| 当日仓库分析 | 仓库日报 |
| 周、月、年度汇总 | 仓库周总结、仓库月总结、仓库年度报告 |
| 来源绑定的功能与实现审阅 | 代码功能分析 |
| 已登记测试结果的解释与验收 | 项目测试审查报告 |
| 超出消息容量的交付 | 报告分篇发布 |

标题以报告类型、统计周期和适用对象标识内容。篇幅、内部编排方式、临时沟通记录
和维护过程不作为功能名称。项目自定义标题沿用其明确约定，历史标题与协议标识保留。

功能名称、章节标题、CLI说明、skill与调度提示使用一致术语。当前配置字段、命令、
模块路径、错误码和发送快照保持兼容；术语整理不触发历史报告重新发布。

## 分析内容与证据

报告内容以目标仓库和统计周期为边界。CES自身的维护、版本升级、配置调整、
调度提示修订、用户要求变更及本次报告的编制过程，不作为目标仓库的功能进展、
问题、建议或知识更新写入业务报告。上述系统维护事项记录在CES维护文档与回执中。
当目标仓库本身就是CES时，按其实际源码变更和统计范围分析，不附加无关的维护说明。

正文不使用“用户更新”“进一步更新”等对话记录，不介绍新增的CES能力。需要解释
统计口径、证据缺失或发布阻断时，仅说明对本报告结果的具体影响，并集中列入附录；
影响主要结论或交付的实际阻断可在正文简要提示。既有证据与授权规则继续执行。

正文以功能目标、修改前后行为、输入输出、调用及数据流、算法、正确性条件和
优化取舍为主，按功能组织并提供源码提交及行引用。重要功能应给出具体输入示例。
问题登记以证据、影响、建议及验收条件为依据。

启用扩展分析时，按[代码功能分析规范](CODE_REVIEW.md)提供背景、数据流、算法、
示例、边界、复杂度、方案比较和验证设计八项内容；不适用项说明具体原因。
正文篇幅与阅读预算为规划参数，不能替代来源审阅或作为分析质量指标。

区分源码观察、静态推导、实际执行、历史记录和验证计划。实测数据标明对应
来源及执行范围；验证计划使用待执行表述。构建通过仅用于确认配置目标的生成结果。

## 结构与表达

先呈现主要功能变化及工程影响，再说明实现、证据、取舍和后续行动。正常构建、
来源绑定、覆盖缺口及追踪记录集中放入附录；实际阻断或与变更直接相关的问题在正文说明。

使用明确状态和范围描述，避免口语、夸张性修饰、过程性自述及重复限制说明。
发布状态采用“已生成”“待发布”“部分发布”“已发布并回读”或“发布受阻”，
分别说明实际完成阶段。修复候选、静态复核和已验证修复按Issue生命周期独立记录。

## 分篇发布与历史记录

超过消息容量时，由报告客户端在同一线程按序分篇，保留完整正文及摘要校验值。
仅在全部篇完成远端回读后记录完整发布；中断时记录已回读范围和待处理项。
未知发送结果先远端对账，成员编辑触发冲突处理。路由、抄送、指派和去重沿用原账本。

历史报告、知识版本、源码引用及发送记录保持可追溯。术语调整适用于后续生成，
历史成品不因文字风格整理而改写或重复通知。执行、测试、Git及GitHub发布仍遵循既有授权。

# GitHub通知与验收

当前通道为GitHub原生指派、@提及和冷却评论提醒。CES不直接发SMTP，不需要GitHub账号到邮箱映射，也不抓取成员私人邮箱。

## 路由

| 类型 | 收件人 | 实现 |
| --- | --- | --- |
| 代码问题与建议 | 来源代码对应作者；无法归属明确列出 | 创建/补充Issue时@、可指派时设置Assignee |
| 日报 | 当日提交对应GitHub作者 | 报告Issue或新快照评论@，notify核验/补充分配待办 |
| 周/月/年总结 | profile配置权限范围内的维护成员 | 报告线程@，notify分配账号待办；超过GitHub指派人数限制明确处理 |
| 逾期问题 | 当前负责人 | track按静默阈值/冷却周期发表评论并@，持久去重 |
| 项目测试审查报告 | testing.project_owners、testing.test_maintainers、通用cc_recipients，以及问题用例匹配的登记开发者 | 独立测试报告Issue/快照评论，合并抄送并回读；不自动改Assignee，归属缺口明确列出 |

## 项目级消息抄送

在每个仓库的外部profile设置`notifications.cc_recipients`（GitHub账号数组），即可给该项目后续发送的日报、周/月/年总结、代码问题/建议、分析补充与逾期提醒统一抄送。模板默认为空数组；例如：

```json
{
  "notifications": {
    "cc_recipients": ["project-owner"]
  }
}
```

编辑时保留notifications中的其他现有字段。增加或删除数组成员即可调整，设置`[]`可关闭。`doctor --config <profile>`显示当前抄送名单；真正发送前会核对账号是目标仓库成员，格式错误、非成员或成员读取失败均停止，不静默漏发。所有账号仅来自外部profile，不在产品中按仓库名称分支。

当前渠道通过原GitHub消息中的“抄送：@账号”实现知会。它不是SMTP的Cc邮件头，也不推断私人邮箱；通知邮件仍由GitHub和收件人的参与/提及偏好决定。账号已是主收件人或已有明确提及时去重，负责人和Assignee仍按原来源规则设置，抄送人不自动成为问题处理人。

发送回执区分`primary_recipients`、`cc_recipients`和合并后的`recipients`，正文回读包括抄送段，个人铃铛/邮件入箱仍独立标记为未核验。报告发送快照包含有效路由配置，相同内容和相同路由不重复通知；新路由在下一次发布时应用，不因修改profile立即重放历史消息。旧归档和发送账本保留，未知POST不自动重发；抄送不绕过Issue提醒冷却。

## 交付状态

1. GitHub接受事件：已回读正文、提及账号、Assignee及远端链接。
2. 账号可见待办：Assigned查询能找到对应问题或报告。
3. 个人提醒/邮件收件：由收件人的GitHub偏好、组织约束和本人确认决定；只有本人确认或独立收件证据才能记录。

发送者与收件人相同时，检查参与/提及通知和自己的更新设置。一次测试已确认不代表之后每封都确认，也不表示站内和邮件两个渠道都收到了；本人未说明渠道时仅记录“提醒已收到，渠道未细分”。

用户明确确认的测试收件保存在仓库外profile指向的验收记录中，包含真实测试链接、确认来源、日期和范围，不作为全体成员永久送达保证。

## 使用与去重

相同语义快照不重复创建报告或评论。发布之后仍执行notify确保待办指派，不能把单纯@视为已经指派。未知POST不重复发送；track只在配置阈值到期时提醒。

GitHub原生通知邮件格式由GitHub控制，不能保证链接之外不含正文。当前产品不保留SMTP试装入口；如未来重新选择SMTP，应另行配置并验收，而不是复用旧试装密钥。

手动与Codex定时器共享同一配置和账本。调度、项目目标和具体成员在外部配置，不写入CES通用实现。
